1. Архитектура системы

1.1 Общая схема

Браузер (SPA React)  ──HTTPS──►  nginx  ──►  Node.js/Express (pm2: wareapp-api, :3001)
                                   │                    │
                                   │ статика dist/      ├──► PostgreSQL «warehouse» (единая БД, мульти-тенант)
                                   │ /uploads (фото)    ├──► AI-провайдер (OpenAI-совместимый API, ключ в .env)
                                   │                    └──► Telegram Bot API (уведомления компаний)

Монолитный backend (один процесс Express) + одностраничный frontend. Всё состояние — в PostgreSQL; файлы (фото товаров, логотипы компаний) — на диске в /uploads, раздаются как статика.

2. Модель данных

2.1 Принцип мульти-тенантности

Все бизнес-таблицы несут company_id (и, где применимо, branch_id). Каждый SQL-запрос фильтруется по скоупу пользователя; для управленческих ролей скоуп вычисляет хелпер getUserBranchIds(user, query): admin — по запросу, founder/director — все филиалы компании (или выбранный), manager — жёстко свой филиал (иначе 403).

2.3 Эволюция схемы

Функция ensureSchema() выполняется при старте процесса: идемпотентные CREATE TABLE IF NOT EXISTS / ALTER TABLE ADD COLUMN IF NOT EXISTS / индексы. Отдельные волны миграций логируются («schema OK», «wave4 (sales) schema OK» и т.д.). Отказ одной необязательной таблицы не роняет чтение (degrade: try/catch с нулевыми значениями).

3. Backend: проектные решения

3.1 API

  • REST поверх /api/*; ответы JSON; ошибки — { error } с корректным HTTP-статусом.
  • Авторизация: middleware auth([roles]) проверяет JWT и роль; скоупинг данных — getUserBranchIds/getBranchFilter.
  • Только параметризованный SQL ($1, $2…); строковая интерполяция допустима лишь для значений из белых списков (например, гранулярность date_trunc).
  • Крупные агрегирующие эндпоинты: /company/dashboard (totals, by_method, sales_trend c авто-гранулярностью час/день/месяц, biz_state c ролевой редакцией, топы, алерты), /company/sales-chart (бакеты периода + prev), /team/kpi, /customers/segments, /risks, /police/alerts и др.
  • Admin-плоскость отделена allowlist-ом маршрутов: оператор платформы не достигает финансовых данных клиентов; журналы для него редактируются.

3.2 Ролевая редакция данных (privacy by design)

  • Менеджеру сервер отдаёт агрегаты «состояния бизнеса» только в долях (equity_ratio/liability_ratio) и тренд в нормированном виде (idx 0..1) — суммы не покидают сервер.
  • В операционных экранах «Продажи» менеджер видит денежные суммы строго своего филиала (осознанное скоуп-послабление).
  • AI-контекст для менеджера не формируется (роль вне AI_ROLES).

3.3 Журнал и «полиция магазина»

  • Единый хелпер audit(req, action, entity, id, old, new, opts) пишет в audit_log; авто-детект подозрительности: скидка >15%, списание >3 шт, возврат, изменение цены, удаление.
  • Алерты «полиции» вычисляются на лету: suspicious-строки журнала + группировка отклонённых продаж (≥3 на продавца, ≥8 — high) с оценкой потерь; статусы «проверено/игнорировано» хранятся по детерминированному id алерта.

3.4 AI-подсистема

  • Системный промпт собирается на сервере: язык ответа, правило «границы данных» (только данные компании, без внешних источников/бенчмарков), роль собеседника, свод данных компании (продажи 24 мес, касса, клиенты, филиалы).
  • Единый вызов OpenAI-совместимого API; таймауты и обработка недоступности провайдера; лог токенов в ai_chat_log; каталог инструментов (toolsCatalog) включается в промпт, чтобы AI подсказывал «куда нажать».

4. Frontend: проектные решения

4.1 Оболочки по ролям

  • founder/director/manager → owner-панель (OwnerShell); cashier/seller/warehouse → операционный Desktop/Mobile POS; admin → админ-оболочка.
  • OwnerShell даёт глобальный контекст BranchScope: выбранный филиал, период (пресеты + произвольный диапазон), язык; все инструменты читают его из контекста.

4.2 Реестр инструментов и хабы

  • modules.js — единственный источник структуры панели: разделы, инструменты, группы сайдбара, счётчики вкладок хабов; матрица HIDDEN_TOOLS по ролям; функции getSectionsForRole/getUserSections учитывают персональные и компанейские отключения.
  • Хаб = компонент TabHub (CombinedTools.jsx): сегмент-контрол вкладок, роль-фильтр вкладок (например, финансовые сценарии симулятора — только учредителю), запоминание активной вкладки в localStorage; каждая вкладка рендерит существующий инструмент без изменений.
  • ToolRouter резолвит URL /owner/:section/:tool → компонент, оборачивая в ErrorBoundary (изоляция сбоев) и хлебные крошки.

4.3 Дизайн-система (канон Confluent-light)

  • Токены в styles.css (scoped .owner-shell): фон #F8FAFD, поверхность #FFFFFF, текст #14284B/#173361, primary denim #173361, акцент-градиент #21B0EA→#1E5AE8, границы #E3E9F2, мягкие тени; тёмные темы запрещены.
  • Иконки — только line-SVG (icons.jsx, штрих 1.8, currentColor); эмодзи вычищаются централизованно (stripEmoji в примитивах ui.jsx — Tile/Card/PageHeader/Badge/Pills/EmptyState), поэтому 60+ файлов инструментов не требуют правок.
  • Числа: Inter + tabular-nums; денежные значения — полные, с разделителями разрядов.
  • Локализация: tt(строка) с fallback-цепочкой словарей; узбекские даты — собственный fmtDate.

4.4 Навигация

  • Сайдбар: Главная → группы РАБОТА / АНАЛИЗ / СИСТЕМА → AI; при сворачивании остаются иконки.
  • CommandPalette (Ctrl+K): поиск по названию и описанию инструментов (описания хабов содержат имена вкладок), клавиатурная навигация, переход по Enter.

5. Безопасность

МеханизмРешение
АутентификацияJWT (секрет из .env, ≥24 симв. в production); bcrypt-хэши; rate-limit 5/15мин на IP+логин
АвторизацияРолевые списки на каждом маршруте; скоупинг company/branch на уровне SQL; PUT/DELETE проверяют принадлежность записи компании
Изоляция adminMiddleware-allowlist: admin достигает только /admin|companies|branches|users|auth|audit-log|role-change-log; прочее — 403; журналы редактируются

Аудитaudit_log со старым/новым значением, IP, ролью; авто-пометка подозрительных операций; журнал событий в панели

6. Развёртывание и эксплуатация

  • Прод: VPS, nginx → статика frontend/dist и proxy /api → pm2-процесс wareapp-api (порт 3001).
  • Деплой: сборка Vite → выгрузка server.js + toolsCatalog.js + dist по SFTP → pm2 restart → smoke (HTTP 200, логи, «schema OK»). После выгрузки статики обязателен chmod -R a+rX.
  • Резервное копирование: ежедневный pg_dump с ротацией.
  • Наблюдаемость: pm2 logs; журнал событий; health-sweep скриптом по ~150 GET-эндпоинтам.
  • Нагрузочное тестирование: отдельный симулятор (Node+Vue+MQTT) гоняет полный цикл через реальный API на [SIM]-компаниях, измеряя ёмкость БД.

7. Ключевые проектные компромиссы

  • Монолит вместо микросервисов — скорость разработки и простота эксплуатации для команды из одного разработчика; горизонтальный рост отложен до реальной потребности.
  • Одна БД на всех тенантов — дешевле и проще; изоляция обеспечивается дисциплиной скоупинга и проверками; строки-миллионники индексированы по (company_id/branch_id, created_at).
  • Вычисляемые алерты вместо материализованных («полиция», риски, аномалии) — нет фоновых воркеров; статусы разрешения хранятся отдельно и мёржатся по детерминированным id.
  • ensureSchema на старте вместо внешних миграторов — идемпотентно и атомарно с релизом кода; требует аккуратности с владельцем таблиц.
  • Хабы с вкладками вместо удаления инструментов — упрощение навигации (116→78 карточек) без потери функциональности и с обратимостью.

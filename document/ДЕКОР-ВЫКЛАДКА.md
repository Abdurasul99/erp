# Сфера «Декор» (Dora Decor) — устройство и выкладка

## Как устроено

```
mywarehouse.uz/decor/login — свой вход «Декора»
              │
   nginx  location /api/decor/  ──►  decor-api  127.0.0.1:3003  (pm2 decor-api)
              │                           │
   location /api/ ──► Wave :3001          база wave_decor (владелец wave_decor_user)
   (не меняется)                          фото и видео: /var/lib/wave-decor/uploads
```

- **Пакет прислан под «платформу сфер»** (учебный центр + ядро + общая админка сфер,
  пакеты `07_edu_kod` и `08_core_mgmt`). Её у нас нет ни в коде, ни на сервере,
  поэтому «Декор» поставлен **отдельным сервисом**, как «Мероприятия»: свой процесс,
  своя база, **свой секрет токенов**. Токен «Декора» не проходит в Wave, токен Wave —
  в «Декор». Wave (`backend/server.js`, база `warehouse`) не меняется вовсе: падение
  «Декора» сайт не роняет.
- **Код сферы — без изменений** (`decor-api/decor/` = `backend/decor/` из пакета),
  кроме одной правки безопасности в `uploads.js` (ниже). Вместо `sphere_db.js` платформы —
  `decor-api/sphere_db.js` (одна база из `.env`), вместо `auth` Wave — своя проверка токена
  (`decor-api/src/app.js`).
- **Компании и учредители** — скриптом `decor-api/scripts/create-company.js` (делает то же,
  что `POST /api/admin/spheres/decor/companies` общей админки: компания, филиал, учредитель,
  нормы, полномочия, ставки, требования к фото, базовые функции). В админке WoW «Декора»
  пока нет. Сотрудников и их входы заводит сам учредитель в разделе «Команда».
- **Экраны** — `frontend/src/decor/` из пакета, маршрут `/decor/*` — отдельная ветка
  приложения (как витрина `/store`): без проверки входа Wave, грузится отдельным файлом.

## Что исправлено в коде пакета (передать разработчику «Декора»)

1. **Загрузка SVG как «фото» → кража токенов (XSS).** Фильтр пускал любой `image/*`.
   SVG — документ со скриптами; миниатюра открывается в новой вкладке через blob на нашем
   домене, и скрипт из «фото» читал бы токены входа («Декора» и Wave). Теперь
   принимаются только JPEG, PNG, WebP, GIF, HEIC/HEIF, AVIF и видео MP4, MOV, WebM, 3GP, MKV.
   Тест проверен «мутацией»: с прежним фильтром SVG принимается и даже засчитывается
   как фото-доказательство. Плюс заголовок `X-Content-Type-Options: nosniff` на всех ответах.
2. **Папка фото по умолчанию была публичной.** `backend/uploads/decor` в их раскладке лежит
   внутри `backend/uploads`, которую Wave отдаёт всем без входа (`app.use('/uploads', static)`).
   Здесь сервис **не стартует**, если папка фото внутри `backend/uploads` или `frontend/dist`.
3. `multer` 2.x вместо 1.4.5 (в 1.4.x известные уязвимости отказа в обслуживании).

## Проверено

- `decor-api`: 13 тестов на настоящем PostgreSQL 16 (PGlite) — миграции D00–D24 по списку
  из `apply_decor_migrations.sh`, `/health` с D23 и D24, создание компании одной транзакцией,
  вход, чужие токены (Wave, без сферы, другая сфера) → 401, ключ повтора обязателен и повтор
  не создаёт дубль, кассир без права на себестоимость → 403, фото PNG принимается и
  отдаётся только своей компании, SVG → 400, заблокированный → 403, отказ старта с
  публичной папкой / тест-хуками / коротким секретом.
- Интерфейс: сборка, 98 тестов, в том числе изоляция «Декора» (не тянет код Wave, стили
  только внутри `.dd`, ветка `/decor/*` без входа Wave).
- Браузер (Chromium, живой стенд): вход учредителя кликами, все 10 разделов, новый лид
  через экран (один, без дубля), вход сохраняется после перезагрузки, телефон 390 px без
  горизонтальной прокрутки, страница входа Wave не грузит код «Декора».
- Тесты самой сферы (формулы 146, API 204, повторы 102, путь заказа 62) в пакет не входили —
  запросить у разработчика «Декора» и прогнать на копии.

## Остатки декора списком

Вещи склада по одной добавляет учредитель («Склад → Декор и износ → Добавить вещь»). Список из тетради —
скриптом из JSON-файла в `decor-api/import/` (формат: `{ "items": [{ "name", "qty", "check"? }] }`):
```powershell
ssh root@207.180.254.241 "cd /var/www/wareapp/decor-api && node scripts/import-items.js --founder doradecor --file import/dora-decor-2026-10-21.json"
```
`qty` — «Куплено, шт»; цена 0 и ресурс 1 — их вписывают на экране (без цены износ в себестоимости = 0).
Вещь с тем же названием уже есть — не трогается, скрипт печатает расхождение. Весь файл одной транзакцией,
повторный запуск ничего не дублирует; `--dry-run` — показать, ничего не записывая. Позиции с `check`
скрипт печатает списком «сверить с тетрадью».

## Склад: журнал и операции (этап 1, D25, 2026-11-01)

Доработка по аудиту фронта — уже наша, не код пакета:
- **Журнал склада** `decor_stock_moves`: «Куплено» меняется только операциями — приход, списание (не больше,
  чем лежит на складе, с причиной), инвентаризация (насчитали на складе − должно быть = разница; при расхождении —
  причина), покупка из фонда («Купил декор»), начальный остаток новой вещи. Сумма журнала по вещи = «Куплено».
  `PUT /items/:id` с `qty_bought` теперь отвечает 400 `use_stock_ops`. Вещам, заведённым до D25, миграция пишет
  одну строку «Остаток до журнала склада».
- **Право «Вести склад» (`manage_items`)**: заводить вещи, менять название, архив, операции. По умолчанию — у кладовщика.
  Цена и ресурс — по-прежнему только «Менять настройки». Миграция меняет ограничение списка действий и добавляет
  строки права всем компаниям (матрица 3 × 11).
- **Экран «Склад → Декор и износ»**: поиск, фильтры (на объектах, проблемы, нет на складе, архив), сортировка;
  окно вещи — название (и на компьютере), операции, архив, история (операции склада + выдачи и возвраты по заказам);
  «Журнал» склада по всей компании со страницами.
- **Выбор вещи с поиском** в калькуляторе и в «Купил декор».

Адреса: `POST /api/decor/items/:id/stock` (`kind`: receipt | writeoff | count), `GET /api/decor/items/:id/history`,
`GET /api/decor/stock-moves?limit=&before=&kind=`. Тесты: `test/stock.test.js`, `test/stock-migration.test.js`.

Выкладка — как обновление ниже: архив `decor-api` → `install.sh` (применит только D25 и перезапустит `decor-api`),
затем интерфейс. Интерфейс собирать **из закоммиченного кода** (`git archive HEAD frontend`), а не из рабочей папки:
в ней могут лежать чужие несохранённые правки.

(**не потерять правку `ALLOWED_MIME` в `uploads.js`**, если она не перенесена к ним),

## Откат

- «Декор»: `pm2 delete decor-api`, вернуть конфиг nginx из копии, путь к которой
  напечатал `install.sh` (`/root/rollback/nginx/….before-decor-ДАТА`), `nginx -t && systemctl reload nginx`.
  Копии конфига — только в `/root/rollback/nginx/`: nginx подключает ВСЕ файлы из
  `sites-enabled/`, и копия рядом с оригиналом читается как второй сайт (так упала первая
  установка 2026-10-26 — «duplicate default server»; `install.sh` теперь сам убирает такие копии).
  База `wave_decor` и фото остаются, Wave не затронут.
- Интерфейс: `cp -a /root/rollback/dist-before-decor/. /var/www/wareapp/frontend/dist/`.

## Бэкап

`/usr/local/bin/wave-decor-backup.sh`, ежедневно в 03:30 (`/etc/cron.d/wave-decor-backup`):
`pg_dump wave_decor` → `/var/backups/wareapp/wave_decor-ДАТА.sql.gz` (14 дней) и копия
новых фото и видео в `/var/backups/wareapp/decor-uploads/`. Это тот же диск сервера:
от удаления спасает, от потери сервера — нет (внешний бэкап — открытый пункт по инфраструктуре).

### Правила предметной области (сводка; подробности — в разделах «Формулы» и «Решения»)
- **Бронь по каждой вещи.** Заказ держит вещи дизайна с `event_date` по `event_date + N` (N «дней на объекте», настройка, по умолчанию 1). Вещь освобождается с даты своего финального возврата (в т.ч. финала 0) или когда по ней на объекте стало 0. «Не вернулось с объекта»: период кончился, по вещи нет финала, на объекте > 0 — вещь занимает склад до возврата. Свободно на D = (куплено − пропавшее в закрытых − недостача под вопросом) − брони других активных заказов на D − не вернувшееся. Для заказа «свободно» — минимум по дням периода. Причина «почему нет» — `freeDetail` (кто держит, откуда не вернулось).
- **Финал по вещи** — один раз, количество может быть 0; после него по этой вещи только «Поздний возврат»; остаток и довыдача после финала не принимаются.
- **Недостача под вопросом**: финал принят, на объекте осталось → для брони вещи уже нет (с даты финала), в себестоимости — предварительно; показывается отдельно (склад, карточка заказа, подсказки; кладовщику без сумм).
- **Поздний возврат (`late_return`)**: вещь нашлась — на склад, недостача уменьшается, износ как у финала. После закрытия: снимок не меняется, движение `after_close` с суммой по цене из снимка + запись `returned_after_close` в `audit_log`; в отчётах — «возвращено после закрытия».
- **Себестоимость по вещам**: вещь с финалом — факт (износ = (final + поздний) × износ_за_1, недостача = на объекте × цена), без финала — план (дизайн × износ_за_1); режимы `plan / partial / fact / closed`. Команда = Σ ставок по уровню и типу заказа; расходники $ = сум ÷ курс; постоянные в месяц = таргет + ремонт_сум ÷ курс + прочие; доля = постоянные ÷ ожидаемое число заказов; полная = прямая + доля; прибыль = цена − полная; цена < полной — красное предупреждение.
- **Закрытие** — только по чек-листу (финал по каждой выданной вещи, оплата полностью в кассе, «Приёмка» одобрена); при закрытии — снимок всей себестоимости (`closed_cost`: недостача окончательная, `shortage_items` с ценами). Открыть закрытый — только учредитель.
- **Полномочия** — матрица должность (`cashier`, `warehouse`, `pm`) × 10 действий (`create_order, change_status, handle_decor, take_money, confirm_money, upload_report, approve_report, pay_team, see_finance, edit_settings`); учредитель и ген. директор — всё. Вход сотруднику создаёт учредитель; должность по уровню: ПМ и ученик → `pm`, кассир → `cashier`, кладовщик → `warehouse`. Суммы сервер отдаёт только с `see_finance` (цены вещей — ещё с `edit_settings`).
- **Деньги**: в кассу (сразу подтверждено) пишет тот, у кого `confirm_money`; с `take_money` — только деньги, принятые самим; «сдал» отмечает принявший; подтверждает только касса. Касса = подтверждённые − выплаты команде. Сдельные начисления — автоматически при одобрении «Приёмки».
- **Функции и панель**: функции компании включает админ Wave (выключенная закрывает свои адреса API); «Управление панелью» (учредитель) только прячет разделы из дока.

### Защита от повторной отправки (D23) — СДЕЛАНО 2026-10-24, ОБЯЗАТЕЛЬНА
Решение пользователя с поправками. Защищены **все** записывающие маршруты сферы; начинали с 14 маршрутов: создание заказа (`POST calc/confirm`, `POST orders`), смена статуса и закрытие (`POST orders/:id/status`), приём оплаты (`POST orders/:id/payments`), «сдал кассиру» (`POST payments/:id/hand`), подтверждение кассой (`POST payments/:id/confirm`), выдача (`POST orders/:id/issue`), довыдача / остаток / финал / поздний возврат (`POST orders/:id/moves`), «принять всё» (`POST orders/:id/final-all`), загрузка отчёта (`POST orders/:id/reports`), одобрение и возврат отчёта (`POST reports/:id/decision`), выплата команде (`POST payroll/pay`).
- **Клиент** (`frontend/src/decor/kit.jsx` → `useActions`, `api.js` → `newKey`): заголовок `Idempotency-Key`; ключ создаётся при нажатии кнопки и живёт, пока сервер не ответил (обрыв связи, тайм-аут, `idem_running`) — повторное нажатие того же действия шлёт тот же ключ; ответ получен (2xx/4xx) — ключ сброшен; другие данные действия (`reset`) — новый ключ. Кнопки заблокированы до ответа. Нет ответа — сообщение «Нет ответа от сервера. Нажмите ещё раз — повтор не создаст дубль».
- **Сервер** (`backend/decor/idem.js`; `common.js` → `tx(fn, req)` / `txFor(req)`): ключ записывается **в той же транзакции**, что и действие (первой строкой, отмечается `done` перед COMMIT) — сохраняется всё или ничего. Повтор выполненного — первый ответ (заголовок `Idempotent-Replay: true`; тело то же, порядок полей может отличаться — JSONB). Тот же ключ с другим телом (`request_hash` = sha256 метода, адреса и тела; порядок полей не важен) или на другой адрес — 409 `idem_mismatch`, ничего не выполняется. Двойное нажатие — второй запрос ждёт первый до 2 минут (`lock_timeout`) и получает его ответ, дольше — 409 `idem_running`; запись `running` старше 2 минут считается `failed` (повтор разрешён). Неверный формат ключа — 400. Записи старше 30 дней удаляются при старте и раз в сутки. В отпечаток тела не попадают пароли: поля с `pass` в имени заменяются на «[скрыто]».
- **Ключ обязателен (поправка пользователя 2026-10-24)**: любой POST / PUT / PATCH / DELETE `/api/decor/*` без `Idempotency-Key` — **400 `idem_missing`** «Нет ключа повторной отправки (Idempotency-Key) — действие не выполнено. Обновите страницу и повторите.», ничего не выполняется. Проверка стоит в общем месте (`access.js` → `idem.needsKey` → `idem.middleware`), поэтому новый маршрут не может её пропустить. Исключения (ничего не записывают в данные заказа): `POST calc/preview` (только считает), `POST auth/login` (до входа), `POST auth/change-password`. Все записывающие маршруты пишут через `txFor(req)` — кроме 14 первых теперь и `PUT orders/:id`, `PUT orders/:id/lines`, `PUT orders/:id/costs`, `POST/PUT items`, `PUT settings`, `settings/panel`, `permissions`, `rates`, `POST/PUT employees`, `POST/PUT employees/:id/login`. Если маршрут принял ключ, но не записал его (забыли `txFor`), сервер пишет в журнал «без записи ключа», а при `DECOR_TEST_HOOKS=1` ставит заголовок `X-Idem-Unclaimed` — тесты API на этом падают.
- **Обязательность**: без таблицы `decor_idempotency` `GET /api/decor/health` отвечает 503 («миграция D23 обязательна»), а записывающий запрос с ключом — **503 `idem_unavailable`** и не выполняется. Молча защита не выключается. Таблица перепроверяется каждые 5 минут и перед ответом 503 (после применения D23 перезапуск не нужен).
- **Тест-хуки** (только при `DECOR_TEST_HOOKS=1`, на рабочем сервере не включать): заголовок `X-Test-Hook: fail-before-commit` — «падение посреди действия», `delay-<мс>` — пауза перед COMMIT (обрыв ответа).
- **Тест** `backend/test/decor_idem.test.js` — 102/102 (Шаг 5: действия склада, отчёты и «сдал» — с фото; «Купил декор» с вещью — склад пополняется один раз; требования; «добавить доказательства»; «без фото → отказ» и при повторе): двойное нажатие (два одновременных запроса — один заказ), обрыв ответа (клиент бросил запрос, повтор получил созданный заказ), падение посреди действия (ничего не сохранилось, повтор выполнился один раз), тот же ключ с $151 вместо $150 (409), тот же ключ на другой адрес (409), неверный ключ (400), повтор каждого из действий без дублей, в т.ч. действий карточки заказа (правка заказа, дизайн, расходы и цена, статус вперёд и назад, вещь, цена вещи) и экранов Шага 4 (лид → калькулятор с `order_id`, отчёт без фото, «вернуть отчёт»). ## Модель данных (`D10_decor_domain.sql`)

- `decor_settings` — курс сум/$, транспорт и расходники по умолчанию, постоянные расходы (таргет $, ремонт и стирка сум, прочее $), ожидаемое число заказов, **N «дней на объекте»**, выключенные разделы панели, счётчик номеров заказов.
- `decor_permissions` — матрица должность (`cashier`, `warehouse`, `pm`) × 10 действий. Учредитель и ген. директор могут всё, в таблице не хранятся.
- `decor_employees` (уровень `pm/trainee/cashier/storekeeper`, вход `user_id` — не у всех), `decor_pay_rates` (ставка по уровню и типу заказа).
- `decor_items` — вещи: куплено, цена $, ресурс заказов.
- `decor_orders` (+ `decor_order_team`, `decor_order_lines` — дизайн = бронь), `decor_payments` (касса или сотрудник; at_pm → handed → confirmed), `decor_reports` + `decor_report_files`, `decor_payroll`.
- `decor_moves` — движение декора по заказу: `issue` (выдача), `extra` (довыдача), `left` (возврат остатка, без износа), `final` (финальный возврат **по вещи**, может быть 0 — «ничего не вернулось»), `late_return` (поздний возврат). `after_close` + `amount_usd` — поздний возврат по уже закрытому заказу и его сумма (D20, D21).
- `decor_orders.closed_cost` — снимок себестоимости при закрытии, включая `shortage_items` (недостача по вещам с ценами на момент закрытия).
- **Изоляция компаний в самой базе:** у каждой таблицы `company_id`, связи — составными ключами `(company_id, id)`. Строка дизайна не может сослаться на вещь другой компании даже при ошибке в API (проверено).
- Ограничения: закрыть заказ без снимка себестоимости нельзя; оплата «в кассу» сразу подтверждена; статусы, типы, N (0–30) — CHECK.

## Формулы (`backend/decor/formulas.js`)

Все формулы ТЗ — в одном файле, чистые функции (данные + «сегодня» → результат). API, подсказки и тесты берут их отсюда.

На объекте по вещи = issue + extra − left − final − late_return.

**Бронь — по каждой вещи (решения 2026-10-22):**
1. Заказ держит вещи дизайна с `event_date` по `event_date + N` (N «дней на объекте» в настройках, по умолчанию 1).
2. Финальный возврат делается **построчно**. Вещь освобождается с даты своего финала (в том числе финала 0) или с даты, когда по ней на объекте стало 0 (всё вернули остатком). Остальные вещи заказа держат бронь дальше: финал по коврам не освобождает ромашки.
3. Вещь «не вернулась с объекта»: период заказа кончился, финала по ней нет, на объекте что-то есть — она занимает склад до возврата.
4. Свободно на D = (куплено − пропавшее в закрытых − недостача под вопросом) − брони других активных заказов, чей период включает D (по не освобождённым вещам) − не вернувшееся с просроченных заказов. Для заказа «свободно» — минимум по дням его периода.
5. «Не вернулось с объекта» показывается по заказу со списком вещей без финала (Бронь, Склад, подсказки AI и главная).

**Недостача под вопросом (решение 2026-10-22):**
- По вещи принят финал, а на объекте что-то осталось → это «недостача под вопросом», пока заказ не закрыт. Для брони вещи уже нет (с даты финала по ней) — не обещать то, чего нет.
- Показывается отдельно: на Складе (`GET warehouse` → `shortage_pending`), в карточке заказа (`shortage: { status: 'pending', items }`), в подсказках (`shortage_pending`: кладовщику — без сумм, учредителю — с суммой).
- В себестоимости — **предварительно** (`cost.shortage_preliminary: true`). Окончательно фиксируется при закрытии заказа в снимке (`closed_cost`, `shortage_preliminary: false`, `shortage_items` с ценами); в карточке `shortage.status = 'fixed'`.

**Себестоимость — тоже по каждой вещи:** вещь с финалом (или с 0 на объекте) — ФАКТ: износ = (final + поздний возврат) × износ_за_1, недостача = на_объекте × цена; вещь без финала — ПЛАН: износ = qty_по_дизайну × износ_за_1. Режим заказа: `plan` → `partial` → `fact` → `closed` (снимок). Без этого при финале только по коврам ромашки, ещё стоящие на объекте, посчитались бы недостачей по полной цене.

**Поздний возврат (`late_return`):** вещь из недостачи нашлась и её привезли. Только после финала по этой вещи (до финала — `409, code: no_final`); не больше, чем не хватает.
- Заказ не закрыт: вещь возвращается на склад, недостача уменьшается, износ на неё — как на финальный возврат.
- Заказ закрыт (решение 2026-10-24): вещь возвращается на склад, **снимок себестоимости не меняется**; движение помечается `after_close` с суммой = кол-во × цена вещи **из снимка** (а не текущая), в `audit_log` — запись `returned_after_close` (заказ, вещь, кол-во, цена, сумма). В отчётах видно, сколько нашлось из списанной недостачи: карточка заказа (`recovered_after_close`), `GET finance/costs` (`recovered_after_close_usd` по заказу и `closed_recovered_usd` итого), главная (`kpi.closed_recovered_usd`); подсказка о недостаче закрытого заказа показывает остаток и пропадает, когда нашлось всё.

**Чек-лист закрытия:** финальный возврат принят **по каждой выданной вещи** (`waiting_final` — какие ещё ждут), оплата полностью в кассе, «Приёмка» одобрена. Закрыть с недостачей под вопросом можно — она фиксируется в снимке.

## Шаг 3: экраны «Склад» и «Калькулятор» (2026-10-24)

Вход — `/decor/login` (свой токен `decor_token`), оболочка как в прототипе: верхняя панель (компания, «ERP · должность», поиск, RU/UZ, AI, уведомления — число подсказок, пользователь), нижний плавающий док с плитками-градиентами (активная увеличена; разделы с выключенной функцией и выключенные учредителем не показываются), баннер раздела с цифрами и кнопками. Разделы следующих шагов пока показывают баннер и пометку «Шаг N».

**Склад** (`/decor/warehouse`, вкладка в адресе `?tab=`): «Не вернулось» и «Недостача под вопросом» — отдельными вкладками с пояснением (плюс «Списано в закрытых заказах» с поздним возвратом); «Заявки на сборку» — по вещам счётчик «Выдать, шт» и «свободно» на период; «На объектах» — по каждой вещи: выдано, остаток, финал, на объекте и действия (Довыдать / Остаток / Финал — до финала по вещи; «Поздний возврат» — после); «Принять всё как финальный возврат» — по вещам без финала, 0 = «ничего не вернулось»; «Декор и износ» — остатки (на складе, на объектах, под вопросом, пропало, свободно сегодня), цена/ресурс/износ и их правка — по полномочиям. Телефон: строки карточками, кнопки от 46 px, действия через окно с крупным счётчиком. Кладовщику суммы не приходят с сервера.

**Калькулятор** (`/decor/calc`): клиент, телефон, адрес, дата (ДД.ММ.ГГГГ), тип, команда (ПМ и ученики — кнопками); вещи с «свободно» **на весь период заказа** (бронь других заказов + не вернувшееся + недостача под вопросом) и подсказкой под строкой, почему не хватает: «на 27 окт, вт: занято: D-105 (1) · не вернулось с D-097 (1)»; себестоимость считает сервер (`POST calc/preview`, через 300 мс после правки) — тем, кто видит деньги; цена и предоплата (предоплата — только у того, кто подтверждает деньги). «Подтвердить» → заказ, бронь на период, заявка на складе, предоплата в кассе → калькулятор очищается, плашка «Заказ D-xxx создан» с переходом к заявке.

**API, добавлено на шаге 3:** `why` в `POST calc/preview` и `GET availability` (формула `freeDetail`: на самом тесном дне периода — `reserved_by`, `not_returned_from`, `pending_shortage_from`, `lost_closed`); `GET items` отдаёт цену и износ только с `see_finance`/`edit_settings`; в `GET warehouse` у недостачи статус заказа — `order_status` (раньше затирался статусом недостачи).

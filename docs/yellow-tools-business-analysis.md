# Анализ жёлтых инструментов и вопросы для бизнеса

Дата анализа: 2026-07-06  
Источник статуса: `frontend/src/owner/modules.js`, поле `wired: false`.

## Краткий вывод

В проекте 15 инструментов помечены жёлтым флажком как `В разработке / Скоро`. Это означает, что реальные данные ещё не подключены.

Из них:

- 10 имеют frontend-макет, но работают на статике или локальном состоянии.
- 5 не заведены в `ToolRouter` под свой `toolId` и открываются как общий `ComingSoon`.
- Для части инструментов уже есть близкие API/таблицы, которые можно использовать как основу.

Главный риск: нельзя просто "подключить данные", пока бизнес не подтвердит процесс, роли, формулы KPI, статусы и источники данных. Иначе получится экран, который выглядит готовым, но не помогает принимать решения.

## Рекомендуемая приоритизация

### Быстрые победы

1. **Конкуренты**  
   Уже есть API и таблица. Нужно подключить UI к `/api/marketing/competitors`, добавить CRUD и уточнить бизнес-поля.

2. **Отзывы**  
   Уже есть `NPS и отзывы`. Нужно решить, является ли жёлтая карточка отдельным reputation-мониторингом или её надо убрать/объединить.

3. **Категорийный менеджмент**  
   Можно считать из существующих `products`, `categories`, `stock_outcome`, `stock_income`, `product_stock`.

4. **Планирование**  
   Можно начать с ручного ввода планов продаж/бюджета и отчёта план-факт.

### Средняя сложность

5. **CJM и точки контакта**  
   Сначала можно сделать управляемые справочники и ручные KPI, затем подключать события.

6. **Адаптация**  
   Можно собрать на базе существующих чеклистов, задач и курсов.

7. **Автоматизация**  
   Начать с безопасных сценариев: создать задачу, создать заказ поставщику, отправить уведомление. Полный движок лучше делать после согласования правил.

### Крупные модули

8. **B2B / B2G и Коммерческие предложения**  
   Требуют полноценной CRM-логики: компании, сделки, стадии, КП, товары, скидки, версии, PDF, отправка, история.

9. **Наборы / BOM**  
   Требуют складских правил: списывать компоненты, приходовать набор, учитывать себестоимость, разборку, брак.

10. **Логистика**  
    Требует отдельной модели доставок, курьеров, статусов, SLA и, возможно, карты/геолокации.

11. **Найм**  
    Требует HR pipeline: вакансии, кандидаты, этапы, оценки, офферы.

12. **Горячая линия**  
    Требует ticket/call-center модели и SLA.

## Общие вопросы бизнесу перед любой реализацией

1. Какой бизнес-результат должен давать этот инструмент: контроль, аналитика, автоматическое действие, отчёт, продажа, экономия времени?
2. Кто основной пользователь: учредитель, гендиректор, менеджер филиала, кассир, склад, HR, продавец?
3. На каком уровне работает инструмент: вся компания, филиал, сотрудник, клиент, товар, поставщик?
4. Какие действия пользователь должен выполнить внутри инструмента: только смотреть, создавать записи, согласовывать, отправлять, экспортировать?
5. Какие данные уже есть в компании, а какие готовы вводить вручную?
6. Кто владелец данных и кто отвечает за актуальность?
7. Какие KPI считать, по каким формулам, за какие периоды?
8. Какие статусы нужны и кто имеет право переводить между статусами?
9. Какие уведомления и алерты нужны?
10. Какие отчёты или экспорты нужны: PDF, Excel, печать, Telegram, email?
11. Какие ограничения доступа должны быть по ролям?
12. Нужен ли аудит изменений: кто изменил, когда, что было до/после?
13. Какие ошибки недопустимы: неверное списание склада, неверная цена, лишняя отправка клиенту, раскрытие данных?
14. Что является MVP, без чего инструмент нельзя считать готовым?
15. Какие 3-5 сценариев бизнес будет проверять при приёмке?

## Вопросы по каждому инструменту

### 1. Стратегия 3 года

Цель инструмента: превратить статичный календарь и годовые цели в управляемую стратегию с KPI, инициативами и ответственными.

Вопросы:

1. Какие стратегические горизонты нужны: 1 год, 3 года, кварталы, месяцы?
2. Какие цели фиксируем: выручка, прибыль, маржа, филиалы, SKU, клиенты, B2B, экспорт?
3. Нужны ли разные стратегии по филиалам или одна стратегия на компанию?
4. Кто создаёт и утверждает стратегию?
5. Какие инициативы должны быть внутри стратегии: маркетинг, закупки, персонал, финансы, склад?
6. У каждой инициативы должен быть ответственный, дедлайн, бюджет, статус?
7. Как связывать стратегию с задачами и чеклистами?
8. Что считать прогрессом: выполнение задач, достижение KPI, ручная оценка?
9. Нужно ли хранить версии стратегии?
10. Сезонный календарь общий для всех клиентов или настраиваемый?

### 2. Конкуренты

Цель инструмента: мониторить конкурентов, цены, ассортимент, сервис и давать рекомендации.

Вопросы:

1. Список конкурентов вводится вручную или импортируется/парсится?
2. Какие поля по конкуренту обязательны: название, сайт, Instagram, адреса, рейтинг, ассортимент, цены, доставка?
3. Нужно сравнивать среднюю цену или цену по конкретным товарам-аналогам?
4. Как сопоставлять наш товар с товаром конкурента?
5. Кто и как часто обновляет цены конкурентов?
6. Какие изменения считать важными: цена изменилась на 5%, появился новый товар, новая точка?
7. Нужны ли алерты по конкурентам?
8. Нужно ли хранить историю цен?
9. Какие рекомендации должен давать инструмент: снизить цену, поднять цену, усилить УТП, добавить товар?
10. Нужно ли разделять конкурентов по регионам/филиалам?

### 3. Категорийный менеджмент

Цель инструмента: управлять ассортиментом по категориям через продажи, маржу, остатки, закупки и поставщиков.

Вопросы:

3. Какие KPI по категории важны: выручка, маржа, оборачиваемость, остаток, GMROI, out-of-stock, доля возвратов?
4. Какой период анализа по умолчанию?
5. Кто отвечает за категорию?
6. Нужно ли задавать план продаж/маржи по категории?
7. Какие рекомендации нужны: расширить, сократить, поднять цену, распродать, дозакупить?
8. Как учитывать сезонность?
9. Нужно ли сравнивать категории между филиалами?
10. Какие действия должны быть из экрана: создать заказ поставщику, создать скидку, создать задачу?

### 4. Наборы / BOM

Цель инструмента: продавать и собирать комплекты из отдельных товаров с корректным складским учётом.

## Предлагаемый план интервью

1. **15 минут: приоритеты**  
   Разложить 15 инструментов на `срочно`, `следующий этап`, `пока оставить макетом`.

2. **30 минут: процессы**  
   Для каждого срочного инструмента пройти путь "кто создаёт -> кто ведёт -> кто утверждает -> какой результат".

3. **30 минут: данные**  
   Зафиксировать источники данных, ручной ввод, обязательные поля и владельца данных.

4. **20 минут: KPI и формулы**  
   Подтвердить расчёты, периоды, пороги алертов.

5. **20 минут: роли и права**  
   Кто видит, кто редактирует, кто утверждает, что должен попасть в аудит.

6. **15 минут: MVP-приёмка**  
   Согласовать 3-5 тестовых сценариев на каждый выбранный инструмент.

## Риски для разработки

1. **Дублирование функциональности**  
   `Отзывы` пересекаются с `NPS и отзывы`; `B2B` пересекается с `Лид-трекером`; `Адаптация` пересекается с курсами, чеклистами и задачами.

2. **Недостаток предметных сущностей**  
   Для наборов, логистики, найма, КП и hotline нет полноценной схемы данных.

3. **Опасные автоматизации**  
   Автоматические SMS, заказы поставщику или изменения склада нельзя включать без лимитов, логов и подтверждений.

4. **Формулы KPI могут быть спорными**  
   План-факт, маржа набора, категория, B2B pipeline и SLA требуют бизнес-подтверждения.

5. **Ролевой доступ**  
   Нужно отдельно подтвердить, какие данные видит менеджер филиала и какие доступны только учредителю/гендиректору.

## Минимальные критерии готовности инструмента

Инструмент можно переводить из жёлтого статуса в готовый, когда:

1. Он читает/пишет реальные данные.
2. Есть понятная модель данных и API.
3. Утверждены роли доступа.
4. Есть обработка пустых состояний и ошибок.
5. Есть хотя бы базовая проверка данных.
6. Есть тестовые сценарии приёмки.
7. Если инструмент создаёт деньги/склад/сообщения, есть аудит и подтверждение действия.
